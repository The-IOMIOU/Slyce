# 0008 — G-code parity harness vs Bambu Studio

**Status:** Accepted. Harness and its unit tests exist (`tools/gcode_parity/`). **Parity has not
been measured yet**: that needs a Bambu Studio binary on the test machine and a full Slyce build.

## Goal

For the same model, printer, filament and process settings, Slyce's G-code should be nearly
identical to Bambu Studio's. "Nearly" must be a number, not a feeling.

## How both slicers are driven

Both have the same headless CLI shape (shared ancestry):

```
<slicer> model.3mf --load-settings "machine.json;process.json" --load-filaments filament.json \
         --slice 0 --export-3mf out.gcode.3mf
```

Sources: [Bambu Studio CLI wiki](https://github.com/bambulab/BambuStudio/wiki/Command-Line-Usage),
[OrcaSlicer CLI wiki](https://www.orcaslicer.com/wiki/cli/cli_mode). Known caveat: Bambu Studio's
CLI is reported to need a display even when headless on Linux
([forum](https://forum.bambulab.com/t/cli-cannot-apply-external-presets/197842)); on Windows this
does not matter.

The `.gcode.3mf` is a zip with `Metadata/plate_<n>.gcode`; the harness extracts it.

## What is compared

The harness parses G-code into a normalised event stream and compares by category:

| Category | Contents | Compared how |
| --- | --- | --- |
| Moves | `G0/G1/G2/G3` end positions (X, Y, Z), feed rates | per-layer path length, move counts, max position delta after aligning by layer |
| Extrusion | total E per layer and per feature type (`; FEATURE:` comments) | relative difference |
| Temperatures | `M104/M109/M140/M190` sequence | exact sequence |
| Fans | `M106/M107` | sequence with values |
| Start / end sequences | lines before the first layer change and after the last | line diff (comments stripped) |
| AMS / tool changes | `T<n>`, `M620`/`M621` blocks | exact sequence |
| Totals | layers, total extrusion, estimated time from header | relative difference |

Comments, blank lines and the slicer's name/version header are ignored. Numbers are compared
with a tolerance (default 1e-3 mm / 1e-5 for E) because float formatting can differ.

## Output

A Markdown + JSON report per case listing each category as `identical`, `within tolerance`, or
`differs`, with the first N differing lines. The summary table is what we quote; we never claim
parity without it.

## Related upstream work

OrcaSlicer keeps its own regression suite in
[OrcaSlicer/orca-test-repo](https://github.com/OrcaSlicer/orca-test-repo) (GPL-3.0): golden-slice
metrics (layer count, estimated time, filament used, summed E) against a stored baseline, a CLI
override sweep, and a GUI-vs-CLI parity harness, run nightly by `.github/workflows/parity_nightly.yml`.
That suite compares OrcaSlicer with *itself*; ours compares Slyce with *Bambu Studio*. The two are
complementary, and its practice of flattening `inherits` before passing presets to the CLI is one we
expect to need.

## Reference cases

`tools/gcode_parity/cases/` holds case definitions (model + preset names). The first set uses
simple open models (calibration cube, cylinder, overhang test) generated by the harness so no
third-party model licences are involved.
